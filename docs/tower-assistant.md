# 塔防山贼助手

本模块是 NimdaDesk 的一个内置业务模块，第一个工具为「渡劫布局分析」。前端位于 `apps/features/tower_assistant/frontend`，存档读取和规划位于同模块的 `backend`，由应用组合层注册。没有迁入以前独立规划器或自动搬迁助手的代码。

## 输入与操作

1. 在游戏中正常保存，打开工具台侧栏的「塔防山贼助手」。
2. 选择包含 `package.nw` 的游戏安装目录，读取存档。默认最近一次保存，也可选择其他存档。
3. 选择要分析的渡劫台，生成方案。渡劫台当前位置保持不变。
4. 查看前后对比地图与编号清单，可以导出一张 SVG 对比图。图上显示人物外观、名字、灵物图标、简称及基础灵气。
5. 点击任意人物或建筑，查看当前/建议位置及灵物变化；人物详情含工作、职业和穿戴装备，灵物详情含等级、品质、基础灵气和五行。人物与建筑同格时，在详情中切换对象。对象详情与编号步骤分别选择，不要求对象必须需要搬迁。

地图及仓库信息来自标明时间和摘要的那一份存档，不是游戏实时状态。本功能不写存档、不启动或控制游戏、不发送搬迁指令。导出的图用于人工执行建议。

## 规划优先级

先用可用的已摆/仓库灵物和现有置物台提高渡劫台灵气，在最高灵气候选中减少需要移动的人物与建筑/设施，再减少灵物更换及搬动距离。人物、设施、资源与建筑的占位、台等级和可搬迁性都参与检查。

「灵气已达上界」与「迁移数量最少」是两种不同结论，界面分别报告。只有取得对应证明的方案才标为精确最优；搜索所得结果会保留限制说明。没有可验证的合法摆法时，返回阻塞原因，不以空步骤或部分布置冒充成功。

仓库灵物参与的是更换现有置物台内容，不凭空创建新台。不拆除实体、不忽略人物占格、不假定未知游戏版本具有相同规则。游戏规则取自当前安装包，具体核对记录见 `tower-game-rules.md`。

当前保持有附属设施的主体建筑、被占用的建筑、原生资源和特殊地形不动；设施仍需留在所属建筑的有效范围内。最优性结论包含这些约束。装卸按先取下、再迁移、最后放置的顺序生成，仓库必须容得下中间取下的灵物；空槽不足时明确阻塞，不假定仓库无限大，也暂不搜索交替装卸顺序。

## 数据与接口

- `tower.discover({})`：只检查程序或工程的父目录是否为游戏安装目录。
- `tower.inspect({gameDir, saveId?})`：列出已识别存档，读取指定或最近存档并返回规范化地图与灵物。
- `tower.analyze({gameDir, saveId?, platformId?})`：重新读取存档、校验规则并生成方案。
- `tower.visuals({gameDir, iconKeys})`：按已核实的动画编号读取对应人物/物品图标，最多 32 个一批；裁成最长 64 像素 PNG 后返回。客户端分批缓存，图标失败时保留文字和分析并显示提示。

方法拒绝额外参数、相对游戏目录、网络路径和非法编号。仅允许读取游戏规则包与被识别的存档文件；模块不提供任意文件读取或脚本执行接口。正常业务错误不会把健康 worker 误当成崩溃。

应用工作区、游戏安装目录和真实存档不入库。前端不在浏览器预览中冒充桌面宿主；浏览器模式会明确提示读取能力不可用。

图标来源为当前游戏包，模块用锁定的 Pillow 读取，不执行其中的脚本。图片只在内存处理并限制压缩文件大小、解码像素和返回大小。导出 SVG 内嵌小图标与文字，包含悬停详情；应用中的点击详情面板不转换成可执行 SVG 脚本。
