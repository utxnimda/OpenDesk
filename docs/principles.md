# OpenDesk 工程基本原则

状态：工程规范，包含用户授权的本地版本化页签包。本文规定必须满足的边界，规则存在不代表已通过运行验证；实际结果以 README、源码和验证记录为准。

本项目从零建设本地桌面工具台。NimdaClaw 提供职责分层的参考，dyd2 提供组件化界面与工具面板的参考；二者的已有业务页签不迁移。后续业务需求由用户逐个提出。

## P01. 明确授权，保持范围

**规则**：实现当前需求所必需的修改；不主动 commit、push、提交 P4 / SVN，不擅自发布或部署。工程初始化授权不包含远端发布授权。用户本轮明确指示优先于仓库内历史约定。

**责任**：所有开发者和自动化代理。

**检查**：开工查看 Git 状态；交付时列出实际修改、验证及版本库操作。不得把无关用户改动纳入本次重写，也不得以清理为理由删除未知文件。可逆实现和必要检查不应被多余确认阻断。

## P02. 框架独立于业务

**规则**：框架只定义通用契约与生命周期，不知道某个应用、游戏、Agent 或业务页签的细节。模块依赖框架公开接口，组合根显式装配二者。框架不得反向导入具体模块。

**责任**：框架维护者保证公开接口；模块维护者保证自身业务闭合。

**检查**：移除所有业务模块后，空工具台仍应能启动、展示基础设置和运行诊断。新增一个普通模块不应要求在导航、窗口、配置和日志等多个框架文件中逐项添加业务分支。

## P03. 模块契约可读、可查、可替换

**规则**：模块具有稳定 ID、显示元数据和显式页面入口；后台能力、设置与命令按需声明。运行时启用状态与构建时是否包含模块分开。跨模块调用必须有公开类型或命名契约。

**检查**：禁用模块后不应残留其后台启动、副作用或导航入口。禁止通过 `window.xxx`、某个 DOM ID、页面顺序或字符串拼接路径偷偷接入功能。

用户已授权本地 `.ndpkg` 导入、新页签添加、多版本并存和选择。自带目录、导入原件/已验证安装目录、个人选择分别管理；失败包保留原件和错误，不加载代码或覆盖可用版本。同 ID/版本异摘要视为冲突。选择不等于成功激活。在线市场、远程自动更新、签名信任链和安全沙箱未因此获得实现授权。

## P04. 三层各有责任

| 层 | 负责 | 边界 |
|---|---|---|
| Vue / TypeScript | 页面、交互、展示状态、输入反馈 | 不直接执行任意系统命令，不持有与后端竞争的业务权威状态 |
| Tauri / Rust | 桌面宿主、窗口、受控 IPC、worker 生命周期、系统入口 | 不重复实现 Python 的业务算法，不发展成第二套业务服务层 |
| Python worker | 工具与业务处理、外部协议适配、业务数据操作 | 不控制桌面窗口生命周期，不直接操纵前端 DOM |
| 专用子进程 | 特定依赖或原生能力 | 通过显式协议报告状态，受清楚的所有权与退出策略约束 |

**检查**：新增功能时能回答“数据归谁、错误由谁产生、进程由谁停止”。同一校验可以在界面提供反馈、在执行边界保证正确性，但业务规则应有唯一权威实现。

## P05. 单一权威与明确状态

**规则**：每种持久状态有唯一拥有者。界面表单草稿、展示缓存与真实持久值分开；操作返回后明确何时刷新。配置保存必须返回成功或可定位的错误，不得先显示成功再忽略落盘失败。

**检查**：文档或代码类型明确配置/数据属于框架还是某个模块。多个调用者同时写入时不得丢失更新；确有并发写需求后再选择队列、事务或版本检查。

## P06. 路径稳定，代码与数据分离

**规则**：程序资源、开发源码、配置模板、用户配置和运行数据分别处理。使用显式解析得到的工程根或应用数据根，不用 `cwd` 推断所有路径，不将用户数据写入安装目录。

**检查**：从不同工作目录启动时仍找到正确资源；包含空格与中文的合法路径可处理。打包运行数据不应回写源码树。开发期覆盖路径必须显式、可诊断，不能在失败后随意猜测其他目录。

配置模板不得含令牌、机器绝对路径或个人数据。密钥使用系统凭据设施或明确的秘密管理边界，不写入 Git、日志或普通配置示例。

OpenDesk 使用独立应用标识 `net.nimda.opendesk` 及其数据目录。当前名称、构建产物和环境变量统一为 OpenDesk / opendesk / OPENDESK；不自动迁移或清理旧应用数据。既有版本历史与历史验证记录保留原始名称和路径，不改写过去的证据，也不将其当作改名后应用已验证的结论。

## P07. 持久化格式有版本

**规则**：持久化对象具有 schema 版本；读入时校验类型、必填字段和版本。变更格式前说明兼容范围和迁移行为。未知的更新版本应报错，不能覆盖成当前默认值。

**检查**：覆盖写前采用原子替换或等价机制；迁移有样例验证，失败保留原始数据。首版无迁移需求时提供版本字段和明确拒绝策略即可，不预建庞大迁移框架。

模块代码与数据目录分开。代码回退不隐含数据回退；旧包不能读取当前 `dataSchema` 时拒绝激活。不能静默恢复旧快照、删除升级后新增记录或覆盖新数据；当前不提供自动迁移/降级数据能力。

## P08. 通信协议显式、有限、可诊断

**规则**：命令、请求、响应、事件和错误结构有明确版本与关联 ID。边界校验消息格式、方法名称、参数及大小。worker 的标准输出仅用于协议，日志写入标准错误或受控日志文件。

**检查**：未知方法、坏 JSON、进程退出、超时及版本不匹配都产生确定错误；不能挂起界面。应用退出后不遗留悬空请求。不能把内部异常堆栈或秘密原样暴露给用户。

模块前端通过 SDK 请求自身 manifest 声明的方法，宿主执行边界再次校验当前包身份与方法。`runtime.*` 和烘焙身份的 `module.identity` 是管理协议，不列入业务 methods。

后续增加事件流和取消协议时必须同时更新生产端、消费端及契约检查。默认不暴露网络监听端口；未来本地 API 属于独立适配层，需要重新定义认证、来源与生命周期。

## P09. 区分命令、任务、服务

| 类型 | 生命周期要求 | 例子 |
|---|---|---|
| 短命令 | 有界等待，一次成功或失败响应 | 读设置、查询宿主信息 |
| 长任务 | 明确开始、进度、取消请求、最终状态 | 批处理、Agent 一轮执行 |
| 常驻服务 | 启动、就绪、健康、停止与异常退出 | 本地后台适配器 |

**规则**：发出取消请求不等于取消完成；收到退出信号不等于资源已经释放。断线或超时后不能推断外部副作用未发生，也不能默认自动重试非幂等操作。

**检查**：界面区分运行、等待、取消中、已取消、失败与未知结果。首版的 worker 调用只是短命令基础；未实现任务持久化、恢复或调度前不能宣称具备任务引擎。

## P10. 进程所有权先于清理

**规则**：记录本应用启动且负责管理的进程；用户自己打开的 IDE、游戏和其他应用属于外部对象。关闭窗口、退出宿主与结束后台任务是不同动作，行为必须明确。

**检查**：不得按程序名批量结束进程；PID 使用时需考虑复用和生命周期。优先通过协议请求正常退出，再对确认属于本应用的进程实施有界的结束策略。不得把“停止 worker”描述成已经停止它未来可能启动的全部外部进程。

## P11. 最少能力，真实隔离边界

**规则**：前端使用命名命令和受限参数；不提供任意 shell、任意文件读写或通用 `exec` 桥接。Tauri capabilities 只授予需要的窗口与功能，不为开发方便默认全开。

**检查**：执行边界重新校验参数；不拼接用户输入形成 shell 命令。需要进程参数时使用参数数组。新的文件、网络或进程能力必须说明目标和拥有者。

Python worker、普通本地插件、独立进程通常仍拥有当前用户权限；进程隔离能减少故障传播，不能自动提供安全沙箱。

## P12. 诊断支持定位，默认保护私人内容

**规则**：统一记录操作名、请求/任务关联 ID、阶段、耗时、结果与错误类别。用户可理解的错误信息和开发诊断细节分开。

**检查**：错误不得被静默吞掉或改成默认成功；日志能关联界面请求和后台处理。默认不记录密钥、完整提示词、剪贴板、文件全文和敏感路径参数。未来日志持久化应有容量与保留策略。

## P13. 依赖明确，构建可重复

**规则**：保留前端及 Rust 锁文件；Python 第三方依赖引入后同样提供可重现约束。禁止开发运行时临时联网安装依赖作为正常启动步骤。Python 依赖环境由工程明确选择，不依赖机器上任意 `python` 恰好可用。

**检查**：构建步骤说明 Node、Rust、Python 和 WebView2 等先决条件；开发成功与发布包可运行分别验证。输出目录不混入源码、虚拟环境、缓存、凭据和运行数据。

每包包含预构建前端和可选独立 worker 运行目录，不依赖使用者的源码/Python。包摘要放在外部索引，不自引用。源码 repository/commit/dirty 如实记录，来源 URL 去除凭据和查询参数；跨暂存目录不能声称 clean。未变输入可复用原包并保留原来源身份，不能为宿主重建重新冒充模块发布。测试包明确标注，不伪造正式历史。

## P14. 验证结论只覆盖实际证据

**规则**：根据变更选择有意义的检查；优先验证契约、失败路径和用户能观察到的行为。不重复实现算法来制造“通过”的测试。

| 证据 | 能说明什么 | 不能替代什么 |
|---|---|---|
| 源码/结构检查 | 依赖方向与逻辑符合规范 | 实际编译、启动 |
| 类型检查 | 静态类型与调用匹配 | 运行时协议正确性 |
| 自动化测试 | 覆盖用例内的行为 | 未覆盖场景和桌面交互 |
| 前端构建 | 前端资源可生成 | Rust 编译、桌面启动 |
| Rust 检查/构建 | 指定目标上的静态检查或编译 | 安装包与 WebView2 运行 |
| 桌面启动/交互 | 当前环境下实测链路 | 其他机器部署、长时间稳定性 |
| 安装包验证 | 指定干净环境的安装与运行 | 所有目标系统兼容性 |

**检查**：完成报告按上述类别分别写“已通过 / 失败 / 未执行”，说明环境限制。不得把只检查源码写成“已验证运行”。

## P15. 文档与代码共同演进

**规则**：README 说明当前能做什么、如何启动、哪些未完成；架构文档说明职责和依赖；模块说明提供接入步骤；AGENTS 提供每次工作的必读入口。

**检查**：接口、目录或启动方式改变时同步对应文档。规划标明“计划/待实现”，示例标明“开发示例”。文档不得承诺尚未实现的托盘、热键、恢复、沙箱或第三方插件能力。

## P16. 按需要抽象，持续保持清晰

**规则**：优先清楚的少量模块与显式装配。没有实际业务需求时，不预建 Agent 工作台、游戏工具、应用中心、数据库体系或工作流引擎。

**检查**：新抽象应解释解决哪一个已知问题、由谁使用、如何验证。新增普通页签的成本应集中在该模块目录和一个明确装配位置；若迫使框架了解业务，先修正边界。

## P17. 宿主、默认包与个人版本独立

**规则**：宿主/core 的中央历史与模块包 manifest 分别权威。独立模块更新不要求提升宿主版本。App 随附索引只声明默认包；用户已选择的精确版本不得在 App 升级后被静默替换。

**检查**：多个版本可并存，每页签只激活当前启用版本。个人选择不兼容时保留选择并说明原因。Git 身份追溯源码，摘要追溯产物，成功激活状态证明实际运行；三者不能互相代替。

获得当次提交与发布授权后，主框架交付源码、App 包和当次随附的正式页签；本仓库开发或更新的正式页签按模块 ID/版本另作独立 Release，保留不同版本供用户手动下载。`config/distribution.json` 的明确清单是构建与公开分发边界，不能因为本机安装或导入过某包而将其上传。测试台/fixture、其他分支或外部导入包、私有模块不得进入本次公开附件。App 仍保留用户原有选择，不因分发清单改变而卸载用户导入内容。构建与发布准备只产生本地文件，不自动获得下一次 commit、push 或上传授权。

## 修改原则的方法

当现实需求与原则冲突时，先说明具体冲突、候选方案及影响，再按用户已经授权的范围决定。用户明确改变原则时，同步本文件与 AGENTS；不要保留互相矛盾的规范。临时限制需要写明原因和取消条件，不能把一次环境障碍变成永久架构要求。
