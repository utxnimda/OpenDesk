# 宿主与模块版本维护

宿主/core 版本与独立页签包版本分别维护。App 发布包含宿主版本和默认模块包；用户后来导入或选择其他版本，不修改宿主版本。

实际交付按 [发布手册](releasing.md) 执行：范围审计、干净构建、独立暂存、源码/标签推送、明确附件上传、远端下载核验与下载索引更新。本文维护版本规则，手册提供可复用的操作顺序；实际完成状态以 [下载索引](downloads.md) 和 [验证记录](verification.md) 为准。

## 权威边界

| 记录 | 权威范围 |
|---|---|
| `config/version.json` | 宿主/core 与已有发布历史 |
| 包内 `manifest.json` | 模块 ID、版本、API、数据 schema 和来源 |
| `app-manifest.json` | 该次 App 默认随附包及摘要 |
| `config/distribution.json` | 本次 App 随附及允许独立公开的正式模块 ID |
| 本机选择与激活状态 | 用户选择和实际运行的精确版本 |

已有塔防子功能历史保持不变，描述过去随 App 交付的事实，不代表当前包版本。共享包内的子功能可以用于分类；拆成独立包并建立接口后才能分别选版本。

OpenDesk 0.6.0 使用独立应用身份，`core.workbench` 为 0.4.0；随附塔防助手 0.1.3 和测试台 1.0.3 的包内容包含当前应用命名。改名通过追加新版本记录表达，保留此前历史中的名称、版本和路径，不覆盖旧发布历史，也不把历史验证改写为当前版本已通过。

## 宿主/core

继续使用：

```powershell
npm run version:prepare -- --file .local/next-release.json
npm run version:sync
npm run version:check
```

现有脚本校验维护者提供的日期、版本、功能变化并追加历史，生成 package/package-lock、Tauri、Cargo 及宿主 CHANGELOG。不得单独手改这些宿主版本，也不借同步更新其他依赖。

现有语义版本和功能递增规则保留：首次能力从 0.1.0 开始，兼容增强升 minor、修复升 patch，不兼容变化明确 breaking，稳定后升 major。脚本只接受正式三段版本，Git 身份单独记录。命令不自动提交、打标签或发布。

## 独立模块包

各模块在自身 manifest 维护版本。单模块更新不强制修改中央历史、宿主 CHANGELOG 或 package/Cargo/Tauri 版本。同模块并行开发自行解决代码和版本冲突，不要求中央变更片段聚合。

同 ID/版本/目标的正式产物不可换为不同摘要；改内容需升版本。构建输出可以重新生成，不能据此覆盖已安装或已发布的版本。Git 标签建议 `modules/<id>/v<version>`；标签追溯源码，摘要追溯实际产物。

包 source 的 repository URL 必须净化，commit 是完整 SHA 或 null，dirty 表示未提交或无法确定完整来源。跨暂存目录构建保守 dirty。复用未改模块的原包时保留其原源码身份，不把宿主新提交当作模块重新发布。fixture 明确测试用途，不创建伪造历史或标签。

## 默认版本、个人选择与数据

App 索引给出随附默认版本；个人精确选择独立保存。App 升级不悄悄换掉个人选择，不兼容则显示原因。安装、选择、激活分别表达，不能把失败显示成升级成功。

hostApi、dataSchema 与包语义版本独立。代码回退不代表数据回退；当前不兼容 schema 直接拒绝，不自动恢复旧快照覆盖升级后数据。

## 交付边界

此前已公开的 App 0.12.0 只随附塔防助手 `0.1.7`；本轮准备 App `0.15.0` 与正式塔防 `0.1.9`，保留本地开发 `0.1.8`。`config/distribution.json` 的 `bundledModules`、`publicModules` 均仅含 `tower-assistant`；构建代码将 `test-lab` 标为测试 fixture，不允许将它加入正式分发列表。测试台源码可以保留为开发测试代码，但其二进制包、本机导入的部署工作台、其他私有或外部分支产物均不上传。此前版本的随附事实保留在历史中，不回写旧记录；用户已导入的包也不会因此被自动卸载或覆盖。

2026-10-22 的公开交付授权对应已发布的 0.12.0 / 塔防 0.1.7。2026-10-23 用户先要求提交现有代码及相关资源，随后明确要求完善发布文档并执行发布流程，且再次排除本机导入的部署工作台。本轮因此可以依次提交发布准备、推送源码与标签、构建和上传审核后的 App/正式页签附件，并记录实际结果；此处记录授权和目标，不预先宣称发布完成。不能从历史授权或本机安装列表推导未来上传清单，也不虚构第三方素材许可证。

| 内容 | 源码 Git | App Release | 独立页签 Release |
|---|---|---|---|
| 宿主、正式模块源码、锁文件、测试、文档 | 纳入审阅提交 | 由对应 Git 标签追溯 | 由对应 Git 标签追溯 |
| 宠物运行 WebM/PNG、来源记录、作者种子/轮廓/处理工具 | 纳入审阅提交 | 仅被前端引用的运行媒体进入 App；作者工具不进入运行时 | 不混入业务页签 |
| 模块自己的前端、worker 与资源 | 提交其源文件 | 只随附白名单中的 `.ndpkg` | 按模块 ID/版本独立打包 |
| EXE、安装器、便携 ZIP、`.ndpkg` | 不写入源码历史 | 审核后作为附件 | 审核后作为附件 |
| 部署工作台、本机 imports/installed、私人配置和运行数据、fixture 包、原始视频及完整母版 | 排除 | 排除 | 排除 |

### 干净提交与本地发布暂存

先审阅源码范围并完成已授权的提交，再从干净工作区构建：

```powershell
npm run build
npm run build:module -- tower-assistant
npm run release:stage -- app
npm run release:stage -- module tower-assistant
```

`build:module` 输出到 `dist/modules/<id>/<version>/`。App 构建自动写入 `dist/app-build.json`，绑定提交、版本、安装器及便携目录逐文件摘要。App 暂存要求该收据对应当前干净提交，实际文件清单与字节未变化。正式模块要求包内来源为本仓库已提交且干净的开发历史、ID 在公开白名单中，并核对内部/外部 manifest 与摘要；可以保留可验证的既有干净祖先提交来源，不能把旧 dirty 包仅改清单冒充新来源。

暂存目录分别为 `dist/releases/app/<App版本>/` 和 `dist/releases/modules/<模块ID>/<模块版本>/`。App 目录包含安装器、便携 ZIP、App 随附清单、当次随附正式页签包、发布清单和校验和；独立页签目录包含 `.ndpkg`、包 manifest、发布清单和校验和。暂存仅生成本地附件，不执行 Git 写入或网络发布；已有版本目录拒绝覆盖。若已有输出有冲突，先保留并检查，不覆盖不可变版本。

App 使用标签 `v<App版本>`，独立页签使用 `modules/<模块ID>/v<模块版本>`。获得当次远端执行授权后，推送审阅后的源码及标签，按明确文件清单创建各自 Release，再下载远端附件核对 SHA-256，并更新[下载索引](downloads.md)。App 随附与独立发布的同一页签必须字节一致。不得递归上传整个 `dist`、fixture、缓存或个人模块目录；本地暂存成功不代表发布完成。

当前 `.github/workflows/check.yml` 只有读取权限：push/tag 触发版本、类型、测试及前端构建，不会自动生成 Windows 安装器、创建 Release 或上传附件。提交代码、打包、暂存、推送和发布仍是明确分开的步骤，不能把“Git 已提交”报告成“可执行版本已发布”。

### 当前开发包转正式包的注意事项

2026-10-23 审计时，0.15.0 是 dirty 工作树的本地候选；塔防 0.1.8 包的来源也为 dirty，`dist/app-build.json` 仍保存旧 0.12.0 收据。这些产物不能直接正式上传。模块内容缓存不把 Git 来源作为输入指纹，因此提交后直接重建仍可能复用旧 dirty 包；发布暂存会拒绝，不能手改 source 元数据伪造干净来源。

0.1.8 已随本地 App 使用，本轮正式交付目标提升到尚未占用的 0.1.9，保留旧包和缓存，从已审阅的干净提交构建新版本。单独提升模块版本不强制提升宿主；本轮保持尚未公开的宿主 0.15.0。发布准备文档与版本先提交，再构建、暂存；远端复核完成后的下载索引和验证记录另作文档提交，不移动实际构建标签。已公开的 0.1.7 及其 Release 不作任何覆盖。

旧历史和标签不覆盖。`version:tags` 只打印宿主历史对应标签，不自动生成模块标签，也不执行 Git 写入。源码提交、标签、包构建、桌面验证与公开发布分别授权、分别记录。

每次执行与改动相关的版本/类型/测试/构建检查。没有本次明确授权不得提交推送 Git/P4/SVN；允许本地出包不等于允许上传 GitHub Release。
