# OpenDesk 虚拟伙伴开发手册

**开工基线：2026-11-02，独立页签 `virtual-partner` 0.1.0。** 本手册用于接下来的开发和验收。第一项工作是在本机导入现有包，用 OpenAI API 完成一次真实对话。第一轮功能迭代让伙伴有可辨认的说话方式，能记住一件有来源的经历，隔天在合适的话题里自然提起。社交账号、后台活动、桌宠形象和直播分阶段接入。

**第一轮进度（2026-11-02）**：P1–P3 已进入本地包 **0.2.0**。现可编辑三组以内的语气示例，确认或略过一条来自用户原话的偏好建议，并将带标题、可选摘录和个人感想的见闻保存到私聊近况中。试用新功能可直接在「功能管理」导入 0.2.0。[使用步骤](virtual-partner.md)

已用两个实际归档包在隔离数据根完成 `0.1.0 → 0.2.0 → 0.1.0 → 0.2.0` 四次启动。升级及回退保留了角色身份、凭据和新版扩展记录。冻结 worker 共处理 7 次显式的本机模拟模型请求。已核验来源链接留在本地、仅标题和有摘录两种输入得到不同标记，以及修改、删除后旧内容不会重新进入模型请求。P4 接话时机的用户体验、个人桌面导入和真实 OpenAI 回合仍须单独验收。开发包按未提交工作树如实标记为 `dirty`，没有对外发布。

## 2. 第一张工单：用 OpenAI 验收 0.1.0

1. 在 OpenDesk 的「功能管理」导入 `dist/modules/virtual-partner/0.1.0/virtual-partner-0.1.0.ndpkg`，启用并打开「虚拟伙伴」。记录实际选中的版本。使用说明见[页签指南](virtual-partner.md)。
2. 在伙伴自己的设置里填写基础地址 `https://api.openai.com/v1`、账户有权使用且支持文本流式 Chat Completions 的模型 ID、该项目的 API Key。模型 ID 由使用者填写，密钥由使用者在本机界面输入。SQLite 中保存角色和记忆，连接配置文件保存密钥引用，密钥由 Windows DPAPI 保护。
3. 输入「记住：我的测试画稿叫纸船」，检查记忆簿中的原话。另开话题询问“我的测试画稿叫什么？”，确认收到真实回答、能查看本次参考的记忆。再把纸船改成纸鸢，重启后验证新称呼，并另外测试忘记后不会重放旧称呼。验收依据包括实际送出的受控测试上下文和持久化结果，不能只凭模型碰巧答对。
4. 使用同一个测试账户检查停止；用模拟服务复现拒绝认证、限流、连接中断、截断流和重复提交。分别记录是否发出请求、是否收到完整回复、是否写入历史。记录模型 ID、日期、版本和结果，使用合成内容；日志和截图排除密钥与真实私聊。真实调用有费用，由测试者显式发起。

**文本模型路线固定为 OpenAI API。** 沿用现有 `POST /v1/chat/completions` 与 `stream: true`。人格指令由模块组装，召回记忆作为有来源的资料随本轮消息传入。现有代码要求非空文本、正常 `finish_reason=stop` 和 `[DONE]` 一起构成成功；缺少终态、取消、超时要向界面返回各自的结果。保留现有本地测试服务即可做日常回归。开工不需要接第二个文本模型服务商，也不需要为了改人格先迁移到另一种 OpenAI 接口。[OpenAI Docs：Chat Completions 流事件](https://developers.openai.com/api/reference/resources/chat/subresources/completions/streaming-events)

## 3. 第一轮迭代：小满有自己的近况

**演示目标。** 周五用户告诉小满“我周末想画一艘纸船”，又分享了一段关于折痕阴影的图文摘录。周日用户换个话题问“今天只想画十分钟，有什么可以试试？”小满可以建议先画一道折痕，并指出这个想法来自那段摘录。如果用户只是给了一个标题，她只能知道标题。如果用户问的是 Git 命令，纸船不会被硬塞进回答。

以下是本轮工单及其验收标准。P1–P3 的本地实现与验证见上方进度，P4 的消息合并和群聊决策留待后续。

| 工单 | 实现入口和工作内容 | 完成条件 |
|---|---|---|
| P1 人格示例 | 在已有角色设置里增加最多 3 组“用户说／伙伴怎样回答”的短例。由后端校验、存储，在上下文预算内组装到人格说明。示例编辑沿用现有档案入口 | 同一条测试消息能比较编辑前后的表达。换话题、模型或重启后角色 ID 不变，用户能够清空示例。旧档案按零条示例读取 |
| P2 可确认的记忆建议 | 在已完成的用户回合上提出一条候选，例如“记住你喜欢用铅笔起稿？”。优先用本地、显式的偏好表达触发；确认调用现有保存记忆的逻辑，拒绝按来源去重 | 用户不点确认时，跨话题检索不到这条偏好。重复点击只存一次。系统不会把模型猜的内容当成用户说过的话，也不为每条消息额外调用模型 |
| P3 第一条经历 | 做“分享给伙伴”入口。首个切片接受用户粘贴的摘录、标题和可选来源链接，标明“用户分享”。用户可选择保存一条有出处的近况，并随时查看、编辑或移除 | 断网也可保存摘录。给出链接但没有正文时不生成“已读正文”记录。跨话题仍能追溯来源；一段被摘录的指令不会触发浏览或发言 |
| P4 私聊回应节奏 | 私聊对显式发送作答；为未来渠道定义“回复、等待、跳过”三种决策。UI 提供实验对话，先评估是否接得自然，再决定是否增加短时消息合并 | 验收用例包含闲聊、具体求助和突然转题。具体求助能直接作答，终止输入或取消回合后不会冒出迟到的回答 |

**第一轮交付门槛。** P1–P3 与上面的两天演示优先。测试通过关闭并重开存储、切换话题来验证连续性，真实跨日的聊天感受仍由使用者评估。P4 先在私聊评估。新版模块包使用 0.2.0，保留已有 0.1.0 原包。版本是否公开以发布记录为准。

## 4. 人格、经历与公开发言的边界

| 信息 | 谁可以改变 | 使用方式 |
|---|---|---|
| 稳定人格、名字、说话示例 | 用户在档案中明确编辑 | 所有展示形式按同一角色 ID 读取。外部网页、群消息和模型输出都只是输入资料 |
| 用户偏好与私聊事实 | 用户明确保存、确认、修正或忘记 | 缺省为私聊范围。保留来源消息和修订号。即使主题高度匹配，也不进入群聊、直播字幕或公开发言的提示词 |
| 近期兴趣和经历 | 记录实际发生的阅读或互动；首版由用户确认保存 | 记录来源、发生时间、看到了什么、伙伴的感想、可用范围。单次记录是经历；多次表现出的兴趣可建议写入档案，由用户确认 |
| 对外行动 | 由渠道适配器执行并报告回执 | 分清“拟了草稿”“等待确认”“已发出”“结果未知”。只有可靠回执能产生“我发过”的经历。超时先核对，不能自动重复评论 |

组装每轮请求时，先用角色 ID、当前渠道、允许使用的范围筛选候选，随后才按相关性和长度挑选。给用户分享的知识附上来源，给伙伴自己的判断保留“感想”属性。公开舞台只读公开投影，不能把完整私聊交给模型后仅靠提示词要求保密。

0.1.0 的 SQLite 是唯一写入者。当前最多检索 3 条相关记忆，近期历史从同话题最多 12 个完整回合内按 14,000 字符预算选取。修正或忘记会提升 `epoch`，旧聊天可阅读，后续请求停止重放旧上下文。新增摘要、候选、来源索引和回忆缓存时，都要继承修订失效机制。比如用户删掉“纸船”后，旧摘要和待确认候选也不能把它带回新对话。[存储实现](../apps/features/virtual_partner/backend/store.py)

**数据变更先于界面联调。** P1 先用一份 0.1.0 合成旧库验证升级、失败回滚和旧版重开。拟新增的逻辑记录是“角色示例”和“经历”；经历至少保存稳定 ID、所属角色、来源类型、来源引用、证据层级、摘录、感想、发生时间、可见范围和修订标记。能被旧包安全忽略的扩展可采用带版本的增量结构。若旧包重开会丢字段、泄露渠道范围或绕过遗忘，必须先设计显式迁移及旧版拒绝策略，校验 manifest 的 `dataSchema` 和数据库版本；不自动清库或降级。两种展示模式都通过命名操作访问同一份数据。[版本维护](versioning.md)

## 5. 之后如何接上网站、社交与直播

**本地 0.8.1 的外出记忆和讨论。** 记忆簿和聊天引用直接读取已有的外出记录，包含 0.7.0 历史。模型生成的留言、用户带回的评论和伙伴回复草稿各自注明出处。普通视频评论发布及收件箱尚无已核对的 B 站开放渠道；接入前需要明确账号权限、授权目标和可验证回执。现有拟稿只使用公开视频文字、有限的语气词和用户主动提供的来评。[使用步骤](virtual-partner.md) · [B 站未列出的能力](https://open.bilibili.com/doc/4/c381daac-4b6d-9ed3-3604-19a78d358eec)

**B 站外出首版（虚拟伙伴 0.7.0）。** `partner.outing.*` 由伙伴自己的 worker 执行。匿名读取限定在 B 站热门与视频详情两个 GET 路由。每轮取最多五个候选，只读取一个视频详情；没有兴趣匹配或可读条目时允许跳过。读到详情先落库，拟稿失败不会丢失来源。聊天最多引用两条相关外出见闻。私聊、记忆与用户分享不会进入拟稿输入。自动外出默认关闭，由可见页签触发，SQLite 的时间与次数预算跨重启生效。真实公开留言、字幕读取及离开页签后继续活动各自需要独立接入。

| 顺序 | 首个可交付切片 | 实机验收 |
|---|---|---|
| B 站内容 | 从用户挑选的一条内容开始，只读实际可取得的标题、简介、字幕或正文。收到标题、读到字幕和取得视频画面是不同证据层级。之后才加入限定主题的定时浏览 | 回答能列出实际读取的来源。网页不可用、需要登录或没有字幕时，能准确说清看到了什么。抓取限定目标、跳转、字节数与时长，遇到本机／内网地址拒绝访问 |
| 一个 QQ 测试群 | 机器人明确加入指定群，先接被 @ 的消息，用消息 ID 去重。小满从本群可用的信息决定回复或跳过。将来允许主动发言时按群单独开启并可随时暂停 | 群 A、群 B 与私聊隔离。重复事件只答一次，暂停后不再排新消息，发送超时显示结果未知。[QQ 机器人消息文档](https://github.com/tencent-connect/bot-docs/blob/main/docs/develop/api-v2/server-inter/message/send-receive/send.md) |
| 小红书、抖音 | 用各自的适配器区分“读取、拟评、回复自己内容、公开评论”四种能力；逐项记录账户权限和平台实测结果。能力未确认时交付只读或草稿 | 对支持的操作先预览目标和文字。账号失效、平台拒绝、限额或用户停用时，停止发送。抖音已列出的授权用户视频评论回复接口，不能当成任意视频评论接口。[抖音接口](https://open.douyin.com/platform/resource/docs/openapi/interaction-management/comment-management-user/video-comment-reply/) |
| 语音与桌宠 | 先接用户提供的文字转音频 API，普通整段返回也可实现“朗读这条回复”。采用句段队列，将生成、播放、播完和被打断分别记录。后续可选 OpenAI `POST /v1/audio/speech` 支持的流式音频。桌宠只绑定 `persona.id`，由既有宠物功能负责窗口、动作和形象 | 用户插话时能停止播放并丢弃未播片段。换展示形象后仍是同一份档案和记忆。接 OpenAI TTS 时清楚标识合成语音。麦克风输入及语音识别另行接入。[OpenAI Docs：语音合成](https://developers.openai.com/api/docs/guides/text-to-speech) |
| B 站直播 | 首先做仅含公开形象、字幕和声音的 OBS 场景，本地录制。之后由用户手动开播，接入获准的直播间弹幕，按优先级挑选一条交给角色回应。自动开播作为单独权限和适配项 | 连续大量弹幕不会无限排队；停止直播能同时停止语音与后续发送。用私聊埋入的独特测试词验证其不会进入直播提示词、字幕、音频或屏幕。分别验收弹幕、舞台、音轨、推流和停播。[B 站直播事件](https://openhome.bilibili.com/doc/4/c7b549c9-d5d6-0331-b510-465ed4107e01) · [OBS 浏览器源](https://obsproject.com/kb/browser-source) |

**自治运行单独设计。** 0.1.0 的 worker 由宿主管理，插件当前只在明确发送时请求模型。引入常驻活动前，先定义用户可见的运行开关、获准账号和目标、活动时间窗、每轮读取／推理／发送预算、冷却和一键停止。默认预算为零，用户启用具体活动后才分配额度。后台和前台必须由同一数据拥有者处理写入；普通页签与后台不能各起一个实例争用独占 SQLite。明确区分离开页面、停用插件和退出 OpenDesk，退出时停止本应用拥有的活动。若需新宿主契约，再按框架规则单独评审。

## 6. 开工与交付检查

在工程根目录执行已有命令：

```powershell
npm run test:partner
npm run test:frontend -- tests/frontend/virtual-partner.test.ts
npm run typecheck
```

第一轮回归基线已有 18 项伙伴后端测试和 2 项前端专项测试。新增功能优先补以下能检出实际问题的场景：

- **旧库升级和遗忘。** 保存、修正、遗忘、重启、换话题，断言发往模拟模型的上下文及来源记录。让旧回复曾经复述该事实，再确认其没有通过派生记录重现。
- **人格与传输。** 编辑人格示例后检查实际组装的请求。一次显式提问只产生一次预期推理。取消、断流、重复请求 ID 或卡在终态前时，都不把部分文本当作成功回合。
- **公开范围。** 使用内容完全相同但范围不同的合成资料。即使私聊资料的相关性更高，群聊或直播请求也不得包含它。未经授权的工具操作在执行边界拒绝。
- **声音和发送。** 后续阶段用“已生成两句，只播放一句即中断”“评论已送达但回执丢失”验收实际播出记录、停止和去重。

实施完成再执行 `npm run check`，按[模块包契约](module-packages.md)给新内容分配新版本后运行 `npm run build:module -- virtual-partner`。记录源码检查、模拟服务、真实 OpenAI、冻结包、原生桌面、外部平台实测各自的结果。本次文档只定义开发工作；Git 提交、推送和对外发布按当次授权执行。

## 7. 参考项目的使用范围
