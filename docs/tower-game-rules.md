# 游戏存档读取与摆放规则

本模块重新核实当前安装的《塔防山贼模拟器》游戏包与实际存档，未恢复旧 Tower 工具的代码。它只分析并显示迁移建议，不启动游戏、不连接游戏运行时、不执行搬迁、不写入游戏存档。

## 读取边界

用户提供本机游戏安装目录。Python 只读取目录内 `package.nw`、`save/eaNsave.dat`、`savedir/eaNsave.dat` 与相应 `saveinfo.dat`。不递归搜索磁盘，不读取备份目录，不接受任意存档文件路径。选择存档使用列表返回的 `save:ea3save.dat` 形式编号；拒绝路径穿越、目录跳转、越界链接和未知编号。

`save` 是游戏工作副本，`savedir` 是游戏同步副本。按存档索引第 7 字段中的毫秒时间排序，时间相同优先 `save`。两个副本均可显式选择，避免内容不一致时悄悄替换。缺少索引时以文件修改时间排序并在界面警告。已有但损坏的索引不会被默默忽略。

数组结构、绑定关系、数值、文件大小与读取期间文件变化均有检查。当前格式为 Construct 三维数组，正式存档通常为 `2501 × 60 × 22`，标识为 `save[0][0][1] == "szmnqea"`。未使用字段允许游戏本身写入的 `null`；参与计算的字段必须是有效数值，不能以零替代未知信息。

## 坐标、占地与数据字段

这里用 `save(x,y,z)` 表示游戏数组访问。主城坐标的原始值比展示坐标大 10000，其他地图的角色和建筑不并入主城。

| 对象 | 数据来源 |
|---|---|
| 建筑 | `z=1`；模板 `y=1`，锚点 `y=2,3`，等阶 `y=5`，占用角色标记 `y=7`，置物台上的灵物槽 `y=9` |
| 人物 | `z=2`；名称 `y=1`，锚点 `y=7,8`，当前工作显示 `y=9` |
| 普通地形 | `save(x,y,6)` |
| 原生资源 | `save(x+50,y,6)`，值为建筑模板编号 |
| 已放设施 | `save(x+150,y,6)` 为设施槽；`z=21` 的 `y=1` 是设施模板、`y=2` 是所属建筑槽 |
| 仓库灵物 | `z=18`；非零 `y=0` 表示存在，模板 `y=1`，等级 `y=2`，品质 `y=4` |
| 已摆灵物 | `z=19`；其余字段同仓库，`y=12` 绑定所属置物台槽 |
| 灵物五行 | `y=5..9` 依次为金、木、水、火、土 |
| 灵物独立基础灵气 | `y=10`，不使用五行数值之和代替 |

`z=13` 是锻造、炼丹等生产队列，虽含坐标和物品字段，不能误认为独立占地资源。设施正在生产的内容也不当作额外建筑阻挡。

建筑宽、高来自 `jz.json` 第 8、9 字段。地图坐标是游戏锚点：3×3 建筑居中，2×2 建筑向正 X、正 Y 方向展开。统一占地左上角为 `x - floor((width-1)/2), y - floor((height-1)/2)`；Y 轴向下增长。

`主地图有效格判定`（事件 1192、表达式 1172–1175）使用地图尺寸 50，山寨等级 `L=save(2,1,0)`，可建矩形四边均包含：

```text
minX = 21 - 2*floor((L+1)/2)
maxX = 30 + 2*ceil((L+1)/2)
minY = 1
maxY = 10 + 2*(L+1)
```

## 渡劫台灵气

渡劫台模板 66，占地 3×3；置物台模板 67，占地 1×1。

`地块范围判定`（事件 6963、表达式 3866、373）判断 `abs(dx)+abs(dy) <= 3`。因此渡劫台锚点半径 3 的菱形，除去渡劫台自身 3×3 占地后，恰有 16 个可用格。距离 2 与距离 3 的贡献相同，没有距离衰减。

`刷新地块灵气`（事件 6980、表达式 3872）为每个置物台分别累加：

```text
贡献 = Math.round(10 * 灵物独立基础灵气 * (1 + 置物台等阶 * 0.15)) / 10
渡劫台灵气 = 范围内所有置物台贡献之和
```

五行使用同样的等级倍率、分别保留一位小数（表达式 3873–3877）。本工具当前目标是渡劫台的独立总灵气，不按五行总和排序，不引入研究、操练或对称布局的旧权重。使用当前已有置物台及其现有等阶，不假设升级、购买或建造新台。

游戏 `取下灵物`、`摆放灵物`、`灵物库取出/存入`（事件 6945–6961）支持通过仓库取放并重新绑定灵物。因此优化候选同时包含仓库和已摆灵物；换物与搬建筑是不同动作。读取时核对 `建筑→灵物` 和 `灵物→建筑` 双向绑定，绑定损坏时停止分析。

取下灵物会占用仓库空槽，不能假定仓库无限大。`灵物库取出` 遍历数组 X 维，寻找 `x>0` 且 `save(x,1,18)<=0` 的空槽。因此容量是数组 X 宽度减 1；读取器提供 `rules.warehouseCapacity/warehouseFreeSlots`，规划器据此逐步核查取下与放置操作。缺失物品身份但残留模板的仓库行视为损坏并拒绝。真实验收存档容量 2500，已用 94，剩余 2406 槽。

## 迁移范围

当前工具固定选定渡劫台的位置。可自由迁移没有附属设施、没有占用角色标记的建筑与置物台。人物作为单格占用，可以先让位，目的地必须是空地；人物现有位置可以和设施、置物台重合，不能因此忽略人物。

游戏 `建筑搬迁`（事件 2193）拒绝 `save(建筑槽,7,1)>0` 的建筑。读取器将这类建筑固定，提示先在游戏中清理占用并保存，不凭附近人物位置猜测该标记对应谁。

有附属设施的主体建筑固定，以免研究、操练、林场等设施失效。已核实的 1×1 主城设施可以迁移，维持所属主体不变。`建立设施范围`（事件 2252–2255）和 `建筑设施范围有效检测`（事件 2561–2588）使用范围 3：

| 主体占地 | 允许设施锚点范围，包含边界 |
|---|---|
| 2×2 | 主体 X、Y 各自减 3 至加 4 |
| 3×3 | 主体 X、Y 各自减 4 至加 4 |

上述矩形需再裁剪到已解锁主城；目的地需为空、没有其他设施。原生资源和特殊地形暂保持原位。设施搬迁不会被建议到范围外；不把“可以放置”与“仍能有效工作”混为一谈。

这些固定对象是本轮规划边界，不能把该范围内的最优值描述成允许任意拆除、移动主体、升级和新建情况下的全局最优。

## Snapshot v1

`reader.discover_saves(game_dir)` 返回含 `id/name/savedAt/gameTime` 的列表。`reader.load_latest(game_dir, save_id=None)` 返回：

- `source`：存档 ID、显示名称、UTC ISO 时间、游戏内时间、实际存档 SHA-256，以及时间来自索引还是文件。
- `bounds`：包含边界的 `minX/maxX/minY/maxY`。
- `entities`：字符串 ID、种类、名称、游戏锚点、宽高、`movable`、占地标记；置物台带等阶及 `itemId`，设施带 `parentId/allowedBounds`，渡劫台带 `currentQi`。
- `items`：`warehouse:N` / `placed:N` 唯一 ID、基础灵气、五行、位置、品质和等级；已摆物品带 `pedestalId`。这些 ID 是本次存档槽，不承诺跨存档稳定。
- `rules`：距离、倍率、舍入、锚点约定、版本签名。
- `warnings`：未保存变化、固定对象、缺失索引等清楚限制。

前端只展示和选取，灵气计算与合法性判断由 Python 模块拥有。没有公开任意文件读取或脚本执行接口。

## 人物、物品详情与图标

当前工作 `job` 来自人物 `save(槽,9,2)` 的实际文字，职业与工作分别显示，不能根据武器猜测当前工作。职业编号来自 `save(槽,6,2)`，对应 `zy.json` 第 1 字段的职业名、第 5 字段的说明。人物外观来自 `save(槽,5,2)`；游戏表达式 731 使用这个字符串选择角色动画。

人物装备槽是 `z=2` 的字段 16..21，依次为武器、手套、腰带、饰品、内丹、宝物，值指向 `z=9` 已穿戴装备记录。读取器同时核对装备字段 7 的所属人物槽和 `wp.json` 字段 6 的槽位类型；不满足时只省略该项详情并报告 `detailWarnings`，不编造武器或职业，不改变摆放分析。装备模板来自字段 1，品质来自字段 5，等级来自字段 6；装备的名称、图标、类型分别为 `wp.json` 字段 1、2、7。品质文本来自游戏 `物品品质文本function`（事件 4888–4894）：1 凡物、2 优秀、3 精致、4 绝世、5 传说、6 神话。灵物品质使用同一文本表，等级与五行仍取实际灵物记录。

人物新增可选字段 `appearance/iconKey/profession/professionDescription/weapon/equipment/detailWarnings`；`weapon` 和 `equipment` 条目包含 `slot/name/type/templateId/iconKey/level/quality/qualityName`。灵物新增 `iconKey/qualityName`，基础灵气和五行无需另算。人物存档的修为等级字段存在境界换算，不直接显示成装备式的 L 等级。

`data.json` 的 `project[3]` 中，第 221 项 `角色形象` 有 309 个动画，第 420 项 `物品图标` 有 806 个动画。动画名对应人物外观，或 `lw.json` / `wp.json` 第 2 字段的物品图标名称。图标只使用相应动画的第一帧及其明确的裁剪位置；例如 `person:B6` 来自 `角色形象-sheet11.webp` 的 `(263,1,312,400)`，`item:兽血1` 来自 `物品图标-sheet1.webp` 的 `(817,1837,100,100)`。它们是游戏地图人物形象和物品图标，不从职业、名称或武器推测头像。

`visuals.load(game_dir, icon_keys)` 每次最多接受 32 个 `person:动画名` / `item:动画名`，读取固定包中的已核实映射，拒绝路径形式。未知但格式正确的名称返回明确警告，并让界面使用文字或轮廓占位。仅允许 `images/角色形象-sheetN.webp`、`images/物品图标-sheetN.webp`；不解压到磁盘，也不开放 ZIP 成员任意读取。当前图集实际压缩体积可达约 4 MiB，因此不能直接通过 2 MiB worker 响应返回整张图集。

游戏模块使用锁定的 Pillow 13.0.0，在内存中裁剪后保持比例缩至最长边 64 像素，生成 PNG。每个图标是独立 sheet，`sprites[iconKey]` 指向 `{sheetId,x:0,y:0,width,height}`，`sheets[sheetId]` 包含 `dataUrl/width/height`，整个结果带 `schemaVersion:1` 和 `warnings`。限制单图集 ZIP 成员 8 MiB、边长 4096、解压像素 16 Mi、单 PNG 32 KiB、JSON 响应 1800 KiB；只短暂解码整张图集，最多缓存 512 个小 PNG，不保留完整图集。缓存以包路径、大小、修改时间、文件身份区分；读取中包发生变化则失败。没有复制游戏原图到仓库，也没有调用外部图片服务。
